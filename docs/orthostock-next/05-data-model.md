# 05 · Data Model

The cloud database is the **complete and only permanent record** of the business. Everything
needed to rebuild the business, and to interpret its history, is stored here: documents,
lines, ledgers, the rates and costs in force at the time, and the audit trail.

## 1. Conventions (all tables)

| Convention | Rule |
|---|---|
| IDs | `uuid` primary keys, generated by the device or server (UUID v7). Legacy UUIDs can be kept as-is at migration |
| Tenancy | `business_id` on every business table (one business today; RLS by membership) |
| Money | `bigint` **fils** (`…_fils`). Never floats |
| Quantities | `numeric(14,3)` (pieces, metres, rolls) |
| Unit costs | `numeric(18,6)` (precision for averages) |
| Rates | VAT in basis points (`500` = 5 %); fx as `numeric(18,8)` |
| Dates | `business_date date` (the business day in Asia/Dubai) + `created_at timestamptz` (when it was recorded) |
| Versioning | Mutable aggregates carry `version int`; every revision is kept in a `*_revisions` table |
| Deletion | Issued financial documents are never deleted: `status = 'void'` with reason. Master data is archived (`archived_at`). Only drafts can be discarded |
| Origin | Documents and ledger rows carry `origin` (`'next'` or `'legacy'`) and `data_quality` (`'ok'`, `'legacy_warning'`, `'needs_review'`, `'incomplete'`). These are designed in now so Legacy history fits later (§4) |
| Change feed | Every row devices cache has `change_seq bigint` from one global sequence, set on every insert/update |
| Audit | Each command writes `audit_events` in the same transaction |

## 2. Entities

### 2.1 Platform and settings

| Table | Key columns | Notes |
|---|---|---|
| `businesses` | name, base_currency (`AED`), timezone (`Asia/Dubai`) | |
| `business_members` | user_id → auth.users, role (`owner`/`manager`/`staff`/`viewer`) | Roles enforced in commands |
| `business_settings` | company name AR/EN, address, phone, email, TRN, licence no., bank line, logo/stamp file ids, invoice notes, display defaults (show TRN, show "TAX") | Current profile |
| `business_settings_revisions` | snapshot, valid_from | So an old invoice can be reprinted with the profile in force at the time |
| `tax_rates` | rate_bp, valid_from | Effective-dated |
| `fx_rates` | currency, rate, valid_from | Default for new events; each event stores its own rate |
| `document_series` | code (`INV`, `PO`, `PAY`, `QT`, `SC`…), prefix, next_number | Numbers assigned by the server, gap-free, never changed |
| `command_receipts` | command_id (pk), type, user, device, status, result, at | Idempotency |
| `audit_events` | seq, at, actor, command_id, entity, entity_id, action, before, after, reason | Append-only |
| `devices` | id, user, last_seen, client_build, pending_reported | Device health |

### 2.2 Catalogue

| `variants` | sku (unique per business), category_id, group_id (nullable), name_ar/en, attributes jsonb, unit, default_sell_price_fils, min_stock, archived_at | The sellable material. No cached stock or cost here |
| `variant_images` | variant_id, storage_path | Private bucket |

### 2.3 Parties

### 2.4 Sales

| Table | Key columns | Notes |
|---|---|---|
| `sales_invoices` | number, customer_id, business_date, status (`draft`/`issued`/`void`), version, tax_mode, vat_rate_bp, subtotal_fils (gross), discount_fils, net_fils, vat_fils, total_fils, paid_fils, settlement_status, display options, notes, issued_at, voided_at, void_reason, provisional_ref (offline) | Totals computed by core at issue/revision; a deferred constraint checks totals = Σ lines (+ VAT) for `data_quality = 'ok'` |
| `sales_invoice_lines` | invoice_id, line_no, variant_id, qty, list_price_fils, unit_price_fils (agreed), discount_alloc_fils, net_fils, vat_fils, is_gift, unit_cost (frozen), cost_fils | Line IDs stable across revisions |
| `sales_invoice_revisions` | invoice_id, version, snapshot jsonb, command_id, reason | Full history of every change |
| `credit_notes` (+ lines) | invoice_id, reason, amounts | If credit notes are chosen (Q2) |
| `quotations` (+ lines) | customer, validity, status, converted_invoice_id | |
| `free_restocks` (+ lines) | supplier_id, invoice_id (nullable), value_fils | Zero-cost stock in, valued at sale-time cost |

### 2.5 Receivables

| Table | Key columns | Notes |
|---|---|---|

| `payment_allocations` | payment_id, target_type (`invoice`/`opening_balance`), target_id, amount_fils | Σ ≤ payment amount |
| `cheques` | payment_id, cheque_no, bank, due_date, status | |
| `cheque_events` | cheque_id, status (`received`/`deposited`/`cleared`/`bounced`), business_date | State machine in core |

### 2.6 Purchasing and payables

| Table | Key columns |
|---|---|
| `purchases` | number, supplier_id, business_date, supplier_ref, status, version, total_fils, paid_fils, settlement_status |
| `purchase_lines` | purchase_id, line_no, variant_id, qty, unit_cost, total_fils |
| `purchase_revisions` | snapshot per version |
| `supplier_payments` | number, supplier_id, business_date, amount_fils, kind (`payment`/`write_off`), method, account_id, status |

### 2.7 Inventory

| Table | Key columns | Notes |
|---|---|---|
| `stock_movements` | variant_id, business_date, kind, qty_delta, unit_cost, source_type, source_id, source_line_id, source_version, command_id | **Append-only. The only stock truth.** Unique per (source, line, version, kind) |
| `stock_levels` | variant_id, qty, avg_cost, last_cost, min_cost, max_cost | Written only by commands in the same transaction; checked nightly against the ledger |
| `stock_counts` (+ lines) | status (`draft`/`posted`), counted qty | Posting creates `count` movements |
| `material_loans`, `material_loan_returns` | customer, variant, qty, dates, note | Loans move stock out and back |

Movement kinds: `opening`, `purchase`, `purchase_reversal`, `sale`, `sale_reversal`,
`free_restock`, `adjustment`, `count`, `loan_out`, `loan_return`, `legacy_balance` (§4).

### 2.8 Money and expenses

| Table | Key columns |
|---|---|
| `money_accounts` | kind (`bank`/`drawer`/`investment`), currency, name |
| `account_entries` | account_id, business_date, amount_fils (signed), source_type, source_id — append-only, created by commands for payments, cleared cheques, expenses, supplier payments, transfers |
| `transfers` | from_account, to_account, amount_from_fils, amount_to_fils, fx_rate |
| `expense_categories` | name_ar/en, type (`business`/`personal`/`home`), icon |
| `expenses` | category_id, business_date, amount (in its currency), currency, fx_rate, amount_fils_aed, account_id, note, status |

### 2.9 Field work

`orders` (customer, status `new→planning→ready→delivered/cancelled`, priority, date),
`order_lines`, `visits` (date, emirate, city, customer, notes).

### 2.10 Personal module (separate schema `personal`, owner-only)

`securities`, `trades` (buy/sell, qty, price, fees, trade_date, funded_from_account),
`trade_matches` (FIFO result, recomputed by core on any change), `investment_cash_entries`
(deposit, withdrawal, dividend, fee, interest, opening adjustment), `projects`, `people`,
`personal_debt_entries`. Personal expenses use `expenses` with personal categories.

### 2.11 Reporting views

`sales_facts`, `stock_facts`, `money_facts`, plus balance views `customer_balances`,
`supplier_balances`, `aging`, `vat_by_period`, `pnl_by_day` (rolled up to month/year). The
views contain no business rules: they only filter, group and sum stored facts (see
[04 §2](04-business-rules-and-deduplication.md#2-the-single-home-of-each-shared-rule-in-next)).

## 3. Can the cloud rebuild everything? Checklist

| Needed later | Stored where |
|---|---|
| Invoices, lines, totals, discounts as issued | `sales_invoices`, `sales_invoice_lines` |
| Every earlier version of an invoice | `sales_invoice_revisions` |
| Purchases and history | `purchases`, `purchase_lines`, `purchase_revisions` |
| Current stock and *why* | `stock_movements` (+ `stock_levels`) |
| Historical COGS | `unit_cost` on lines and sale movements |
| VAT history | `vat_rate_bp`, `vat_fils` per invoice; `tax_rates` with dates |
| Payments, cheques and their states | `customer_payments`, `payment_allocations`, `cheques`, `cheque_events` |
| Debts | Documents + allocations + `opening_balances` |
| Cash and bank | `account_entries`, `transfers` |
| Settings needed to read old documents | `business_settings_revisions`, `tax_rates`, `fx_rates`, per-event rates |
| Who did what | `audit_events` |
| Files (logos, stamps, images) | Supabase Storage (included in backups) |

Nothing in this list lives only on a device. A device caches parts of it and queues new
commands. Pending commands are the **only** device-only data, and they are visible (count and
age) until they reach the server ([06](06-cloud-offline-sync.md)).

## 4. Designed now for Legacy history later

The migration happens after Next is complete ([08](08-legacy-migration.md)), but the model
must accept Legacy's history **without forcing fake data into it**. These Legacy situations do
not fit a clean model naturally, so each has a planned place now:

| Legacy situation | Planned handling in the Next model |
|---|---|
| Legacy record IDs (mostly UUIDs; some like `singleton`, `user-<email>`, `ln_…`) | UUID primary keys accept Legacy UUIDs unchanged; others get a deterministic UUID v5. A `legacy_links` table (added at migration) maps both ways |
| Invoice numbers `INV-00001…`, `PO-…` | `document_series` starts after the highest Legacy number; Legacy numbers kept exactly; `document_aliases` for numbers Legacy's auto-renumbering replaced |
| Invoices whose lines do not add up, or with **no lines at all** | `data_quality = 'needs_review'` / `'incomplete'`; the totals constraint applies only to `data_quality = 'ok'`; the stored total stays the historical fact |
| Taxed invoices without a stored VAT amount | `vat_fils` = stored total − net (never today's rate); `data_quality = 'legacy_warning'` if the implied rate is not a known rate |
| Old invoices whose discount was baked into the unit price | Lines store the recovered agreed price plus a `legacy_warning`; the stored net is the fact |
| Payments stored as an array on the invoice, addressed by index | Become `customer_payments` + allocations with deterministic IDs |
| `paidAmount` larger than the payment log (unlogged payments) | An undated payment `as_of_date = null` with `legacy_warning` (the same rule Legacy's statement uses) |
| Opening debts without a date | `opening_balances.as_of_date` nullable; aging reports them as "undated", as Legacy does |
| Cheques without status | Default `received`, marked `legacy_warning` |
| Stock ledgers with no opening movement, toggled (`isActive`) or `rebuilt` movements | Live movements imported; a `legacy_balance` movement bridges any gap to Legacy's stored stock figure, clearly labelled and reported, never hidden |
| COGS (`avgCostAtSale`) and cost snapshots | Copied as historical facts; never recomputed |
| Voided, purged and "returned" invoices | `void` with reason (`legacy_void`, `legacy_purged`, `legacy_returned`); purged ones keep a zero-amount stub plus the raw record |
| Customer opening payments, material loans, personal-debt transactions (arrays) | Rows in their own tables with deterministic IDs |
| Hidden 1:1 "shell" products | Collapsed: the variant without a group |
| USD expenses without a historical rate | `fx_rate` = the Legacy rate at migration time, `legacy_warning` |
| Investment cash flows tagged with the wrong currency, stale realised P&L | Investment account treated as USD; FIFO recomputed by core and compared with Legacy's stored figures |
| Client-written Legacy audit log | Its own read-only table `legacy_audit_events`, separate from Next's audit |
| Legacy users and password hashes | Not migrated; users are invited by email |
| Legacy fields Next does not model | Kept verbatim in `legacy_raw_records` (table, id, payload, checksum), so nothing is lost |

These columns (`origin`, `data_quality`, nullable historical dates, the `legacy_balance`
movement kind, void reasons) exist from the first migration file. The migration-only tables
(`legacy_links`, `legacy_raw_records`, `legacy_audit_events`, `migration_runs`,
`migration_issues`) are added in the migration phase.
